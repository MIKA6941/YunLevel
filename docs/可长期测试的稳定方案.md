# YunLevel 可长期测试的稳定方案

版本：v1.0
建立日期：2026-09-28
适用范围：`YunLevel/` 云版（三级液位 + 换热器，Node 网关 + C++ 双内核 + 原生前端）
关联：`docs/项目进度.md`、`docs/交接须知的注意文件.md`、`docs/评分说明.txt`

---

## 0. 一句话方针

**每一轮测试都产出三样东西**：一份 `测试-YYYYMMDD-第NN轮.md` 记录、一个可复现的缺陷清单、一条能对比的回归基线。
没有记录的一轮测试等于没做。

## 1. 为什么需要这份方案

### 1.1 当前的结构性问题

| 问题 | 现状 | 后果 |
| --- | --- | --- |
| **没有版本控制（最要紧）** | `git` 未安装，`YunLevel/` 也不是 git 仓库 | 无法 diff、无法回滚、无法 bisect 回归；改坏了只能靠 `backups/` 里的 tar.gz 手工回退 |
| 工作目录被临时文件污染 | 根目录散落 4 个 `.tmp-*` 片段（`.tmp-spec-block.js` 13 KB、`.tmp-tank-block.txt`、`.tmp-hx-pid.html`、`.tmp-marker.txt`）和残留的 `.test-data-teacher/` | 这些是历史改动过程的中间产物，会被误当成源码读；`.dockerignore` 靠 `.tmp-*` 规则才排除掉，说明它们确实在打包流程里 |
| `data/` 混着测试垃圾 | `data/` 下有 `browser-test/`、`cloud-test-20260921/`、`cloud-test-20260921b/`、`smoke-project-controls/`、`runtime/` | 正式数据与测试数据同目录，做数据体检时会扫到脏数据，结论不可信 |
| 无统一入口 | `package.json` 只有 `check`（9 个文件的 `node --check`）和 `build:engine`，**没有 `test` 脚本** | 测试要靠人记住三条命令和执行顺序，漏一步就得出假绿 |
| 冒烟测试是单文件线性脚本 | `scripts/smoke-e2e.js` 全流程在一个 `try` 里，**157 个断言** | 任何一步失败就跳到 `catch`，**后面 100+ 个断言全部不执行**，覆盖面瞬间塌缩 |
| 版本无指纹 | 部署包有 SHA256 打印，但源码本身没有版本号写进产物 | 线上跑的是哪版代码无法自证 |

### 1.2 已有测试资产（不要重写，要保护）

| 资产 | 规模 | 层次 | 状态 |
| --- | --- | --- | --- |
| `native-hx/selftest_hx.cpp` | 50 断言 | 换热器内核 | 覆盖物理代数、A/B 工况、`Ki=1/Ti`、回路表规则、蒸汽路、状态魔数 |
| `scripts/smoke-e2e.js` | 157 断言 | 全链路 | 登录/名册/回路/PID/历史/存恢复/评分/双模型隔离/魔数防串 |
| `selftest.cpp`（桌面版根目录） | 72 断言 | 桌面版内核 | 日志显示 `ALL PASS` |
| `singletank_test.cpp` | 18 断言 | 桌面版单罐 | 日志显示 18/18 通过，时间步无关性已验证 |
| `scripts/build-engine.js` | — | 构建 | 双内核编译；hx 源文件缺失时**只跳过不报错**（零回归设计） |

**基线数字（回归时对照，掉了就是回归）**：
`smoke-e2e` 157 断言 / `selftest_hx` 50 断言 / `selftest` 72 断言 / `singletank` 18 断言。

### 1.3 环境实况（2026-09-28 实测）

- Node **v24.16.0**（要求 ≥18，✅）
- MinGW g++ 在 `<MinGW 的 bin 目录>`（不在 PATH，`build-engine.js` 有硬编码兜底，✅）
- **Docker 未安装** → 本地无法验证镜像构建，只能验证内核+网关
- **git 未安装** → 无法做版本 diff
- 源码目录完整：`native/`、`native-hx/`、`server/`、`public/`、`scripts/`、`docs/` 均在位，可直接跑测试
- 无浏览器自动化环境（`.playwright-cli/` 是 09-22 的空壳，只有 4 个日志文件）

## 2. 测试金字塔：六层

从下往上，**每层都必须全绿才允许进下一层**。层与层的失败后果不同：L0 挂了就什么都别测，L5 挂了可以明天再说。

```
L5  人工体验测试   ← 学生/老师真实走一遍，产出"不好用"清单（不可自动化，每月至少 1 轮）
L4  数据体检       ← 跑完后扫描 data/ 全部文件，抓异常值（每轮必跑）
L3  场景剧本       ← 角色化剧本：学生建回路→老师巡视→评分→批改（每轮必跑）
L2  端到端冒烟     ← smoke-e2e.js 改造版，分段可重跑（每轮必跑）
L1  内核自检       ← selftest_hx / selftest / singletank（每轮必跑）
L0  静态与构建     ← node --check + 双内核编译（每轮必跑，秒级）
```

### L0 静态与构建（门槛，10 秒）

```powershell
cd <项目目录>
npm run check            # 9 个 JS 文件语法
npm run build:engine     # 产出 native/build/YunEngine.exe + native-hx/build/HxEngine.exe
```

**通过判据**：
- `node --check` 全部 exit 0
- 两个 `.exe` 都存在且时间戳是本轮
- `-Wall -Wextra` **零 warning**（有 warning 就是有隐患，记为 W 级问题）

**注意**：hx 内核是 `required: false`。构建"成功"但 `HxEngine.exe` 不存在的情况会被静默跳过 —— 所以 L0 结束后**必须显式断言两个文件都存在**，不能只看退出码。

### L1 内核自检（每轮必跑，秒级）

```powershell
# 换热器
native-hx\build\HxEngine.exe      # 先确保已构建
g++ -O2 -std=c++17 -Wall -Wextra -static -o native-hx\build\selftest_hx.exe `
    native-hx\selftest_hx.cpp native-hx\hx_model.cpp native\pid.cpp
native-hx\build\selftest_hx.exe   # 期望：50 checks, 0 failures

# 桌面版（如果本轮改动涉及 native/pid.cpp 或 native/score.cpp）
.\build_mingw.bat
.\selftest.exe                      # 期望：72 项 ALL PASS
.\singletank_test.exe               # 期望：18/18 通过
```

**为什么 L1 不能省**：cloud 版和桌面版**共用同一份 `native/pid.cpp`**（README 明确写了：保证 `Ki = 1/Ti` 只有一个实现）。改 `pid.cpp` 会同时影响两条产品线，且云版冒烟测试**不会**发现积分口径的细微偏差（它只验 `Ti` 原样存储和 `1/Ti` 推导，不验积分项数值）。`selftest_hx.cpp` 里的 `PidStep iTerm = (1/Ti)*integral` 断言才是真正的守门人。

### L2 端到端冒烟（改造后每轮必跑）

**改造点（第一优先级的工程任务）**：

1. **分段可重跑**：加 `SMOKE_ONLY=boot|roster|student|loop|score|hx|isolation|logout`，
   跑到指定 section 结束；加 `SMOKE_FROM=xxx` 从指定 section 开始。
2. **断言不中断**：每个 `section()` 内部自己 try/catch，失败记入 `failures` 但**继续往下跑**。
   现在是一个失败全灭，必须改掉 —— 否则"157 断言"是虚的，实际一轮可能只跑了 20 个。
3. **计数校验**：结束时断言 `passed + failed === 157`。少了说明有 section 被跳过，要报出来。
4. **Windows / Linux 双跑**：`enginePids()` 现在用 PowerShell 查进程，Linux 上必然失效。
   改成读 PID 文件或 `pgrep`，让同一份脚本能在服务器容器里跑。

**环境准备**：

```powershell
$env:SMOKE_PORT = 8097      # 默认 8097；端口冲突时换
$env:SMOKE_KEEP = '0'       # '1' 保留数据目录供事后取证
node scripts\smoke-e2e.js
```

**脚本自己已经做得好的地方**（别改）：临时数据目录隔离、备用端口、结束后清理泄漏的 `YunEngine` 进程、
`SMOKE_KEEP=1` 保留现场。这几点保证了"反复跑不会污染彼此"，是长期可跑的前提。

## 4. L3 角色剧本：模拟学生和老师的真实使用

设计原则：**按"人一天怎么用"来写，不按接口来写**。每条剧本都标注了自动化可行性。

### 4.1 学生剧本

#### S-01 首次登录（每轮必跑）
```
1. 打开 http://<host>:8080，输入班级码 你的班级码
2. 输错学号     → 应报"学号不在名单中"，页面不跳转
3. 输错姓名     → 应报姓名不匹配（服务端 403）
4. 输对         → 进控制区，液位三罐静止、无水
5. 观察：首屏是否需要滚动才能看到主要按钮？
```
断言：冷态 `sim_time=0`、`running=false`、`loops=0`、三罐液位为 0。
体验项：首屏信息密度、错误提示是否说清"哪里错了"。

#### S-02 搭一条回路（每轮必跑，PID 教学核心）
```
1. 选 PV=LI102、MV=FV102 → 加回路
2. 重复加同样的 PV+MV   → 应报"该组合已存在"
3. 换一个 PV 但用同一个 MV → 应报"该阀门已被占用"
4. 填 Kp=0.5, Ti=60, Td=0, 正作用, 自动
5. Ti 填 0 → 应拒绝并提示"Ti 必须大于 0"
6. 启动泵 P101=100%，开 FV101=100%
7. 启动仿真，等 60 s
8. 看液位是否上升；看开度是否在 0..100 内；看 PV 有没有 NaN/跳变
```
断言：液位随进水上升、回路输出有限且在 0..100、TI 口径正确（`Ki=1/Ti`）。
体验项：从"点加回路"到"看到液位动起来"要几步？学生第一次会不会搭错？

#### S-03 串级（桌面版有，云版要确认）
```
1. 主回路 PV=LI103 → MV=FV103
2. 副回路 PV=LI102 → MV=FV102
3. 切串级模式，观察两级是否真的协调（副回路跟着主回路的偏差动）
```
体验项：串级是本项目教学重点之一，学生能否自己拼出来？

#### S-04 暂停 / 继续 / 保存 / 退出（每轮必跑）
```
1. 运行中暂停 → 状态应冻结（sim_time 不再走）
2. 暂停中保存 → 应允许（脚本已验）
3. **运行中（未暂停）保存 → 应拒绝 400**（脚本已验，这是对的）
4. 退出登录 → token 失效，旧 token 再访问应 401
5. 重新登录 → 应恢复上次画面，但**仿真固定为未启动**
```
体验项：第 5 条"恢复了却要手动再点启动"，学生会不会以为坏了？这是**已知的可疑设计**，
每轮都问一次学生视角，攒够证据再提改动。

#### S-05 上传云端方案（每轮必跑）
```
1. 存到云端槽位 2
2. 查云端状态，应显示已存时间
3. 从槽位 2 恢复 → 回路数、SP 都应一致，且 running=false
4. 试槽位 1（教师专用）→ 学生应被拒
5. 教师未开 allowStudentUpload 时，学生上传应被拒
```
断言：换热器槽位与液位槽位**互不可见**（脚本已验）。

#### S-06 换热器模型（每轮必跑）
```
1. 教师未开放时，学生登录页**不应出现**换热器选项
2. 教师开放后，登录页出现
3. 进入后：TI1104 / TI1103 / FI1105 有读数，**不应出现 LI101/LI102/LI103**
4. 推荐工况：TI1104→FV1102 单回路，480 降到 450
5. 看曲线，TI1104 通道**必须有真实数值，不能是一串 null**
```
第 5 条是**已修过的历史 bug**（历史通道曾写死成液位位号），必须每轮回归。

#### S-07 30 分钟评分全程（每轮必跑，耗时最长）
```
1. 非冷态点"开始评分" → 应拒绝并提示先回冷态
2. 未选方案就"开始评分" → 应拒绝
3. 选单罐方案 + 评分对象 → 开始评分（清空两套回路卡、回冷态、开始计时）
4. 搭回路、调 PID、跑满 1800 s
5. 到点：应自动结束、提示"评分结束"、跳结果页、右上角显示"评分结束 限时 00:30:00"
6. 结果页：总分 + 四类分项 + 三罐指标（稳态/MAE/超调/低限/高限/溢流/空罐）
7. 再点"评分结果"标签 → 应可反复查看
8. 结束后继续跑仿真 → 分数应**封存不再累计**
9. 查评分记录 → 应新增一条，含时间/方案/对象/总分/分项/回路快照/PID 快照
10. 导出 CSV → 打开验证内容
11. "回到冷态" → 关闭本次评分，退回控制区
```
断言：`sessionT` 递增、到点自动结束、结束事件只触发一次、结束后 `run_at_end` 不再增长。
**这条剧本是本项目"教学可用性"的核心，必须真跑满 1800 s，不能用 `TICK` 加速糊弄。**

#### S-08 断线重连（建议每 2 轮跑 1 次）
```
1. 仿真运行中，直接关浏览器标签页（不发 logout）
2. 30 s 后重新登录同一账号同一模型
3. 应能重新进入，状态恢复为未启动
4. 若提示"已登录" → 说明旧会话未回收，需要管理员介入（脚本已验这个拒绝路径）
```

### 4.2 教师剧本

#### T-01 班级与名单管理（每轮必跑）
```
1. 新建班级 → 自动生成班级码
2. 用**相同班级码**再建 → 应拒绝
3. 改名、改码、删除班级
4. 加学生 → 重复加同一学号应拒绝
5. 改学生姓名 → 旧姓名应立即失效（脚本已验 403）
6. **禁用学生** → 该生所有模型的会话应同时失效（脚本已验 hx 侧）
7. 删除学生 → 其历史数据如何处理？（数据体检要看）
8. 导出名单 CSV → Excel 打开中文不乱码
9. 导入名单：Excel / CSV / 手动粘贴，三种方式
10. 导入选"覆盖"和"合并"，结果应符合所选语义
```
第 9/10 条是 **P0 缺口，接口从未被自动化测过**，而它是教师每学期开课必做的第一件事。

#### T-02 模型开关（每轮必跑）
```
1. 关闭换热器 → 学生登录页选项消失，直连 URL 也进不去（脚本已验 403）
2. 打开换热器 → 选项出现
3. 确认液位模型**始终**保持开放（脚本已验）
```

#### T-03 课堂巡视（每轮必跑）
```
1. 教师登录 → 课堂演示会话，**不应出现在学生在线列表里**（脚本已验 ownerRole 过滤）
2. 看板上能看到全班在线学生、每人回路参数、各自曲线
3. 看板按 全部/液位/换热器 筛选，筛选结果**不串模型**（脚本已验）
4. 点某个学生 → 看他的详情与曲线（**接口未测**）
5. 教师加载某学生的云端方案 → 自己接管控制，验证学生画面
6. 加载 hx 方案时，教师会话应自动切到 hx 内核（脚本已验）
7. 跨模型传参：tank 教师加载 hx 方案，应返回 `modelId: 'hx'`（脚本已验）
```

#### T-04 评分与成绩（每轮必跑）
```
1. 评分记录列表（**接口未测**）
2. 按模型筛选、按班级筛选
3. 导出评分 CSV → 应含"实验模型"列（脚本已验）
4. 云端导出：ZIP 里的目录名、参数汇总、曲线 PNG 文件名都应带模型名
   （脚本已验"换热器"/"全部模型"字样，**但没验 ZIP 内部结构**）
5. 清空评分记录（**接口未测，误点=数据丢失，风险 P0**）
```

#### T-05 备份与恢复（每轮必跑）
```
1. 备份整个 data/ 目录
2. 还原到一个干净目录
```

## 5. L4 数据体检：抓"数据不正常"

自动化测试只能证明接口返回 200，**不能证明返回的数据是对的**。
每轮测试结束必须跑一遍数据扫描。

### 5.1 扫描范围

`data/` 下全部内容：

```
data/classes.json                                  名单
data/state/*.bin                                   液位状态（tank 魔数 0x594C5631）
data/hx-state/*.bin                                换热器状态（hx 魔数 0x594C4858）
data/history/*.json                                液位曲线（16 通道）
data/hx-history/*.json                             换热器曲线（17 通道）
data/submissions/  data/hx-submissions/            云端方案
data/teacher_backups/  data/hx-teacher_backups/    教师备份
data/score_records.jsonl                           评分记录
```

### 5.2 硬性异常（见到就是 BUG，无条件记）

| # | 检查项 | 判据 |
| --- | --- | --- |
| D-01 | **NaN / Infinity** | 任何数值字段出现 `NaN`、`Infinity`、`-Infinity` |
| D-02 | `null` 冒充数值 | 曲线通道里出现 `null` 而不是数字（hx 通道曾因此全 null） |
| D-03 | 液位越界 | `h1/h2/h3` 不在 `[0, 100]` |
| D-04 | 温度越界 | `ti1104/ti1103/twater` 出现负值或 > 1000 ℃ |
| D-05 | 流量负值 | `qin/q12/q23/qout/fi1105/fuel/mw` 为负 |
| D-06 | 开度越界 | `pump/fv101..fv104/fv1101/fv1102/fv1105` 不在 `[0, 100]` |
| D-07 | **通道数不对** | 液位必须 16 通道，换热器必须 17 通道 |
| D-08 | **通道长度不齐** | 同一 history 对象里所有通道长度必须相等 |
| D-09 | **时间不单调** | `t` 通道出现回退或大量重复（除采样点边界） |
| D-10 | **时间戳倒退** | `t` 应单调不减；倒退 = 竞态 |
| D-11 | **魔数错位** | `state/*.bin` 首 4 字节必须是 `YLV1`(0x594C5631)；`hx-state/*.bin` 必须是 `YLHX`(0x594C4858)。串了 = 数据污染 |
| D-12 | **跨模型目录混放** | `hx-*` 目录里不允许出现液位位号，反之亦然 |
| D-13 | 文件截断 | `.bin` 长度异常（应与历史记录条数相关）；`.jsonl` 末行不完整 |
| D-14 | 评分记录字段缺失 | `score_records.jsonl` 每行必须有结束时间/方案/对象/总分/四类分项 |
| D-15 | **分数越界** | 总分不在 `[0, 100]`，或分项之和不等于总分 |
| D-16 | 孤儿文件 | `state/` 里的文件在 `classes.json` 中找不到对应学号（学生被删后残留） |
| D-17 | 学生状态互相污染 | 同一学号在 tank 和 hx 的历史内容应当**完全不同**（不是同一份数据复制） |
| D-18 | 会话数超限 | `YUN_MAX_SESSIONS` 生效后，第 N+1 个登录应 503 |

### 5.3 统计性异常（记为观察项，累积判断）

| # | 检查项 | 为什么重要 |
| --- | --- | --- |
| S-01 | 曲线**长时间完全不动** | PV/MV 全平，可能仿真卡死 |
| S-02 | 输出**长期贴在 0% 或 100%** | 饱和，PID 参数不可用或方向反了 |
| S-03 | 液位**来回大幅震荡** | 整定不当 / 积分饱和 |
| S-04 | 评分记录**长期为空** | 评分链路坏了但没人发现 |
| S-05 | 单个学生文件**明显大于其他** | 写入去重失效，磁盘会被撑爆 |
| S-06 | 同一时间戳出现**两条不同记录** | 竞态 |
| S-07 | 曲线点数**顶到上限 1800** 之后不再增长 | 上限逻辑可能截断了活跃数据 |
| S-08 | 稳态误差**始终 > 5 pt** | 参数模板需要重调（桌面版基线：单回路 ≈92~94 分，串级 ≈90~92 分） |

### 5.4 数据体检执行方式

`scripts/data-audit.js`（**第01轮已建成**）：

```powershell
node scripts\data-audit.js                        # 扫 data/
node scripts\data-audit.js --dir .test-data-smoke\keep
node scripts\data-audit.js --json                 # 机器可读
```

退出码 0 = 无硬性异常，1 = 有硬性异常，2 = 目录不存在。

**注意**：现有 `smoke-e2e.js` 里的 `KEEP_DATA` 保留机制可以直接复用 ——
跑测试时带 `SMOKE_KEEP=1`，测完对保留目录做体检，形成"行为 + 数据"双证据链。
（第01轮起，`smoke-e2e.js` 与 `scripts/round01/*` 的数据目录都写在仓库内的 `.test-data-smoke/` / `.test-data-round01/`，
不再落系统临时目录，方便事后取证与归档；两者都已进 `.dockerignore`。）

## 6. L5 人工体验：挖"不好用"的地方

自动化测不出"难受"。这一层靠人，**但必须有结构，否则永远只是"感觉有点难用"**。

### 6.1 三个角色各自独立走一遍

| 角色 | 画像 | 最关心 |
| --- | --- | --- |
| **学生** | 第一次接触 PID 的大二学生，5 节课内要交作业 | 能不能自己把回路搭对？参数填错知不知道为什么错？看到液位动有没有成就感？ |
| **实验/授课老师** | 每学期重复用这套系统，1 个班 40~60 人 | 开课准备多久？换模型方不方便？上课能不能投屏演示？导出成绩方不方便？ |
| **运维/管理** | 维护服务器的人 | 出故障怎么定位？备份能恢复吗？升级会不会丢数据？ |

### 6.2 每轮必问的 12 个问题

按顺序问，**不要引导**，记录原话：

**学生**
1. 从打开页面到第一次让液位动起来，用了多久？卡在哪一步？
2. 搭回路时，哪一步最不确定？"PV 选哪个"清楚吗？
3. 参数填错了，提示能让你知道**该怎么改**吗，还是只说"错了"？
4. 曲线看不懂的时候，你怎么办？页面哪里能帮你？
5. 换成热器模型，和液位模型的界面差别大吗？

**老师**
6. 新学期第一次用，从拿到地址到能上课，准备工作花多久？
7. 导入 40 人名单，你实际操作了几步？中间出过错吗？
8. 课堂上要投屏演示，界面在投影仪上看得清吗？
9. 下课要收 40 份作业，导出一次能拿到全部吗？
10. 学生做错了，你发现问题的路径是什么？找得到吗？

**运维**
11. 服务器出问题，你能在 5 分钟内判断是"引擎挂了"还是"网关挂了"还是"数据坏了"吗？
12. 你敢直接跑 `docker compose up -d --build` 升级吗？升级完怎么确认学生数据没丢？

### 6.3 体验问题的记录格式

每条必须写清 **场景 → 期望 → 实际 → 卡点 → 建议**，缺一项不算数。

```
【问题】教师导入名单时，Excel 粘贴到文本框后点导入，提示"格式不正确"，但不说哪一行错
【场景】T-01 第 9 步，40 人名单
【期望】明确指出第 N 行、学号重复
【实际】只有一句"格式不正确"，只能自己一行行试
【卡点】40 行要试 40 次，一节课就过去了
【建议】错误信息带上行号和原因
【复现】教师端 /api/teacher/classes/:id/import，Excel 2007+ 格式
【严重度】P0（教师开课必经）
```

**积累规则**：同一个问题**连续 3 轮被不同人独立提出**，自动升级为 P0 并进 backlog。
单轮提出但别人没遇到，标 `?` 存疑，不进 backlog。

## 8. 版本基线与回归

### 8.1 每轮必须归档

```
backups/YunLevel-baseline-YYYYMMDD-第NN轮.tar.gz      源码快照
backups/YunLevel-baseline-YYYYMMDD-第NN轮.sha256      指纹
docs/测试记录/测试-YYYYMMDD-第NN轮.md                 记录
```

`backups/` 已有先例可循：`YunLevel-tank-KNOWN-GOOD-20260923.tar.gz` + `.sha256` + `manifest.txt` + 恢复说明。

### 8.2 回归规则

新版本到来时：

1. 先在新版本上跑 L0~L2 全套
2. 任何断言数**低于基线**（157 / 50 / 72 / 18）→ 立即停止，先查是断言丢了还是逻辑变了
3. 与 KNOWN-GOOD 版本**双向对比**：同一剧本在两个版本各跑一遍，差异项逐条判定
4. 三个关键分数不得下降：**单回路系统评分 ≈92~94、串级系统评分 ≈90~92、时间步无关性 < 5 pt @60s / < 1 pt @600s**
   > ⚠️ **第01轮修正**：上面三个数字来自**桌面版** `..\selftest.exe`（旧 `score.cpp`，含 `safe=20 ben=9`）。
   > 云版 `native/score.cpp` 是评分 v2（安全改**倒扣**、液位**收益 0**），**液位单对象/系统的天花板只有 70 分**（op 20 + ctrl 50）。
   > 第01轮云版实测：单对象 480 s = **46.14**、系统 1500 s = **58.87**。
   > **基线必须按模型分开定义**，否则会把"正常"判成"回归"。下轮前先补齐云版 hx 评分的基线数字。
5. 回归全绿才允许部署

### 8.3 部署前后

`deploy-yunlevel.ps1` 已做：部署前自动 `tar` 备份 `data/`、备份 `docker-compose.yml`、`docker compose up -d --build`。
